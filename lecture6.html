Understanding Project Cost

The Big Picture

Every activity in a project uses resources (workers, machines, materials), and resources cost money. Naturally, the total project cost depends on how long the project takes.

The surprising part: making a project take less time doesn't always save money — sometimes it costs more. And making it take more time also costs more. There is a sweet spot in the middle — called the optimum schedule — where total cost is lowest.

📉 Direct Cost

The cost of materials, equipment, and labour used to perform each individual activity.

↓ Decreases as project duration increases. Why? With more time, you can use fewer workers doing normal hours instead of expensive overtime, and avoid renting extra equipment.

Example: Finishing a wall in 2 days costs more (overtime) than finishing it in 4 days at normal pace.

📈 Indirect Cost

Overhead costs not linked to any specific activity — things like site rent, management salaries, utilities, insurance, and administrative overhead. These are sub-divided into fixed and variable indirect costs.

↑ Increases as project duration increases. Why? The longer the project runs, the more overhead accumulates — you pay rent, salaries, and utilities every single day.

Example: A site office costs $ 500/day regardless of how much work is done.

⚖️ Total Cost = Direct + Indirect

Since direct cost decreases with time and indirect cost increases with time, their sum forms a U-shaped curve. The bottom of this U is the optimum project duration — the point where total cost is minimised.

Our goal in project crashing is to find and work towards this optimum point intelligently.

// TIME–COST TRADE-OFF CURVE — why there's an optimum in the middle

💡 Key insight: We don't want to crash a project as much as physically possible — we want to find the duration where total cost is minimised. Crashing too much drives direct costs way up while indirect savings become negligible.
What is Project Crashing?

Definition

Project crashing is the process of deliberately shortening a project's duration by adding extra resources to one or more critical activities — at an additional cost. We are essentially "buying" time.

The core principle: only critical activities can shorten the overall project duration. Speeding up a non-critical activity wastes money because the project still must wait for the critical path to finish.

WHY ONLY CRITICAL ACTIVITIES? Think of it this way: if your project takes 30 days because of the critical path, finishing a non-critical activity in 2 days instead of 5 days changes nothing about the project end date — it simply adds slack to that activity. You've paid more for zero benefit.
The Cost Slope Formula

Before we can decide which activity to crash, we need to know how much each activity costs to crash per unit of time saved. This is the cost slope.

Think of it as: "How many extra dollars do I spend for every extra day (or week) I save?" A lower cost slope = cheaper to crash = crash this one first.

Cost Slope — the additional cost per unit of time saved Cost Slope (S) = (Crash Cost − Normal Cost) ÷ (Normal Time − Crash Time)
                S = (CC − NC) ÷ (ND − CD) CC = Crash Cost (what it costs with maximum extra resources)
NC = Normal Cost (what it costs under normal conditions)
ND = Normal Duration  |  CD = Crash Duration (minimum achievable time)
ND − CD = how many days/weeks CAN be saved by crashing this activity
📐 Example: If a task normally takes 10 days at $5,000, but can be done in 7 days at $8,000 —
Cost Slope = (8,000 − 5,000) ÷ (10 − 7) = $1,000 per day saved.
This means every day you crash this activity costs $1,000 extra.
The 9 Steps of Project Crashing
1
Find the Critical Path using CPM. List all paths from start to finish. The longest path is the critical path — it determines the project duration. All activities on this path are "critical activities."
Non-critical activities have "float" (spare time) and do NOT control the project end date.
2
Calculate the Cost Slope for every activity using the formula above. Build a table — you'll refer to it throughout the crashing process.
3
Crash the critical activity with the lowest cost slope first. This gives you the maximum time saving at the minimum extra cost. Add the crashing cost to get the new total direct cost.
You can only crash an activity to its crash duration — you cannot go below that, no matter how much money you spend.
4
Watch for new critical paths emerging. As you crash and shorten the critical path, other paths may "catch up" and become critical too. When multiple critical paths exist, crashing only ONE of them is not enough — you need to crash one activity on each critical path simultaneously.
If you don't crash all critical paths at once, the project duration doesn't actually decrease — the other critical path still controls the end date.
5
When multiple paths are critical, evaluate all crash combinations and pick the one with the lowest combined cost slope. This requires some analysis — see Example 1 for a clear demonstration.
6
Update the network with the new (crashed) durations and costs. Re-draw or re-annotate your network diagram. Re-identify the critical path(s) from scratch.
7
Repeat until no further crashing is possible (all activities on all critical paths are at their crash durations, or your target is reached). Record total cost = normal direct cost + all crashing costs + indirect cost.
8
Prepare a cost table listing total cost for each project duration you've computed. This is your time-cost trade-off summary.
9
Identify the optimum. The duration with the lowest total cost in your table is the optimum project schedule. If a deadline is given, simply stop crashing once you reach that deadline.

Key Takeaways
🎯

Only crash critical activities

Only activities on the critical path control project duration. Crashing a non-critical activity wastes money — it just adds more slack/float to a path that already has spare time.

📊

Always pick lowest slope first

Among all crashable critical activities, always select the one with the lowest cost slope — that's how you get the maximum time reduction for the minimum extra spending.

⚠️

New critical paths emerge

As you shorten the critical path, other paths catch up. Once multiple critical paths exist, you must crash one activity on EACH simultaneously — or the project duration won't actually decrease.

⚖️

Optimum = minimum total cost

Track total cost (direct + indirect) at each duration. The minimum point on your cost table is the optimum schedule. Crashing beyond this point makes the project more expensive overall.

🔁

Crashing is iterative

You crash one step at a time, re-checking the critical path after each step. Never assume the critical path stays the same — it changes as activities are compressed.

🚫

Crash duration is a hard limit

No activity can go below its crash duration — no matter how much money you spend. The crash duration represents the physical limit (e.g., concrete must cure for a minimum time).
